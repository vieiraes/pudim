paralelo (segurança, desempenho/correção, produto/skills), cada achado conferido no código.

arquivos versionados, 500 specs e 400 páginas Next.

Linhas citadas são do estado do código **antes** das correções desta data. A coluna "Estado"
diz o que foi feito nesta rodada.

### 3.2 Riscos de confiança para um QA

1. **Verde enganoso**: E2E seletiva (2 de 50) que passa dá CONFORME. → Agora o status vira "CONFORME (parcial)" com selo próprio quando a última E2E foi seletiva.
2. **Vermelho que não limpa**: possível bug sem estado "resolvido"; "Bug no produto" bloqueia por 14 dias fixos; qualquer arquivo com 0% dá ATENÇÃO para sempre. → `.qa/config.json` com `ignorar[]` e `bloqueiaDias`; investigação com linha `Resolvido: sim` sai do bloqueio. Pendente: estado "resolvido" para possíveis bugs.
3. **Número diferente do oficial**: o Pudim mede com o `coverageInclude` dele, não com a config do projeto. → O painel passa a mostrar "medido com: <include>". Pendente: opção "usar a configuração do projeto".
4. **"Possível bug" errado** custa mais credibilidade do que bug não achado. → K7, K15, K16.
5. **Filtro de teste falso reprovando teste bom do time** (mock do alvo reprova o arquivo inteiro; Page Object em outro arquivo). → As skills só rodam o filtro nos arquivos que o Pudim criou; teste do time nunca é "reprovado". Pendente: seguir imports para o Page Object no filtro.
6. **Testes que só confirmam o código** (caracterização). → Pendente: Stryker no arquivo-alvo (ver 4).

### 3.3 Validação em projeto próprio

A revisão de desempenho mediu num projeto real da máquina (CondoTech), em modo leitura. Isso
não se repete: o Pudim ganhou `exemplos/banco-digital/`, um internet banking fictício com os
cenários que os achados exigiam (React Router com `lazy`, aliases via `tsconfig.app.json`,
Page Object com `goto`, `.qa/areas.json`, bug proposital). A suíte `scripts/test.sh` roda contra
ele, e o E2E real do exemplo passa (6 de 6).
